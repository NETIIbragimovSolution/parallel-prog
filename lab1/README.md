# Лабораторная работа: параллельное численное интегрирование

**Вариант 1.** Функция: f(x) = (1+x) / (2+3x)², интервал интегрирования [1; 3].
**Метод:** левых прямоугольников: I ≈ h·Σf(a + i·h), i = 0..n-1, h = (b-a)/n.

Реализовано три независимых бинарника — каждый в своём процессе, чтобы
замеры одной технологии не зависели от разогрева/остывания CPU другой:

- **`sequential`** — прямой однопоточный расчёт, без единого потока. Служит
  эталоном по времени и точности.
- **`parallel_posix`** — то же вычисление на нескольких ядрах через
  **POSIX threads** (`pthread_create`/`pthread_join`).
- **`parallel_stdthread`** — то же самое через **std::thread**.

Диапазон индексов `[0, n)` делится на непрерывные блоки — по одному на поток,
каждый поток считает свою частичную сумму, результаты потом суммируются и
умножаются на h. Гонок данных нет: каждый поток пишет только в свою ячейку.
Общая часть (функция варианта, первообразная, метод левых прямоугольников,
проверка точности) вынесена в `integration.hpp` и используется всеми тремя
программами.

## Сборка и запуск

```bash
g++ -O2 -std=c++17 sequential.cpp -o sequential
g++ -O2 -std=c++17 -pthread parallel_posix.cpp report.cpp -o parallel_posix
g++ -O2 -std=c++17 parallel_stdthread.cpp report.cpp -o parallel_stdthread

./sequential
./parallel_posix
./parallel_stdthread
```

`sequential` запросит только `n` — количество разбиений (шаг h = (b-a)/n).

`parallel_posix`/`parallel_stdthread` запросят три значения (п.4 задания):

1. `n` — количество разбиений;
2. количество потоков для **основного вычисления** (`main_threads`);
3. максимальное количество потоков для **тестирования производительности**
   (`max_threads`; таблица строится для потоков 1..max_threads).

Вывод `sequential`: время выполнения, результат, точное значение интеграла,
погрешность и проверка точности 10⁻⁶.

Вывод `parallel_posix`/`parallel_stdthread`:

- таблица тестирования по потокам (1..max_threads) — время, результат,
  ускорение и эффективность относительно однопоточного запуска той же
  программы (для сравнения с полностью последовательным расчётом
  используйте `./sequential`);
- CSV-файл (`results_posix.csv` или `results_stdthread.csv`) с теми же
  данными;
- **основной расчёт**: сравнение 1 потока и `main_threads` потоков — время,
  результат, фактическое ускорение, идеальное (линейное) ускорение
  (= `main_threads`) и эффективность относительно идеала;
- точное значение интеграла (аналитически), фактическая погрешность и
  проверка точности 10⁻⁶.

Запускайте `parallel_posix` и `parallel_stdthread` по отдельности (не в одном
скрипте подряд без паузы) — если гонять их вплотную одну за другой, вторая
программа может замеряться на уже нагретом от первой CPU, что искажает
сравнение. Если нужна максимально чистая картина, делайте паузу между
запусками (10-20 секунд), чтобы чип остыл.

### Устойчивость замеров

Каждый замер времени берётся как **медиана** по `REPEATS = 5` запускам
(не среднее) — так один случайный выброс (например, когда планировщик macOS
на гибридных P+E-ядрах поставил поток на медленное E-ядро) не тянет
результат на себя. Прогрев перед таблицей делается на 1 потоке и на
максимальном числе потоков — конкретно 1-поточный прогон прогревается
отдельно, потому что именно он чаще всего страдал от случайного размещения
на медленное ядро (и портил всю кривую эффективности, делая её локально
растущей вместо ожидаемого монотонного падения).

На маленьких n (недостаточно работы, чтобы окупить создание потоков)
эффективность всё равно будет ниже 100% и падать с числом потоков — это
физически корректно, накладные расходы на поток (~15-20 мкс на данной
машине) просто перевешивают выигрыш. Кроссовер: параллелить имеет смысл
примерно от n > P·OH/t_iter, где OH — накладные расходы на поток, t_iter —
время одной итерации (для этой задачи ≈ 1 нс) — то есть от n ~ 3·10⁴ для
2 потоков и n ~ 1.3·10⁵ для 8 потоков; для уверенного эффекта, как и
рекомендовано выше, лучше брать n ≥ 10⁷.
